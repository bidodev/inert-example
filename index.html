Why this combination
<dialog> alone
Handles the modal — renders above content, manages the backdrop, supports showModal() / close() natively.
inert alone
Freezes any element's subtree — no clicks, no tab navigation, screen readers skip it. One attribute, zero JS event soup.
Together
Dialog gets all focus. Page behind becomes completely unreachable. Keyboard, pointer, and assistive tech all agree.
vs. old patterns
No pointer-events: none hacks, no manual focus traps, no aria-hidden juggling. Native, accessible, ~94% browser support.

FAQ
Does inert block scrolling?
No — inert does not block scrolling. It blocks clicks, focus, tabbing, text selection, find-in-page, and screen readers — but wheel and touch scroll still work on an inert subtree. If you need to freeze scroll too, add overflow: hidden separately (for example on <body> while the modal is open).
Doesn't showModal() already do this automatically?
Yes — for <dialog> + showModal(), setting inert on the background is redundant. The browser puts the dialog in the top layer and automatically blocks interaction, focus, and assistive tech access to everything outside it. In this demo, we set inert explicitly just to visualize what's happening.

Where inert is genuinely useful on its own:
  • dialog.show() (non-modal) — doesn't block the background, so you'd add inert manually.
  • Custom modals not built on <dialog> (e.g. a <div> overlay).
  • Non-modal cases: disabling a panel during loading, freezing a form section, offscreen slide-out menus.
Is inert useful for side panels?
Yes — arguably a better fit than the dialog case. Most drawers and side panels aren't built with <dialog> because they need custom slide-in animations and edge-anchored positioning, so they don't get the top-layer free ride. There are two scenarios worth handling:

1. Panel open — freeze the background. Set inert on the main content while the panel is open. No clicks or tabbing leak through, and screen readers skip the frozen area.

2. Panel closed — mark the panel itself inert. A common a11y bug: a panel slid off-screen via transform: translateX(100%) is visually hidden but still in the tab order, so keyboard users can tab into invisible content and get stuck. display: none and visibility: hidden also remove elements from the tab order, but they kill your slide-out transition. inert lets you keep the animation and stay accessible.

See the second demo above — toggling the panel flips inert on both the background and the panel.
